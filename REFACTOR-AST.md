## 1. Зачем

Одна причина, остальное — следствия.

**Роль буквы в слоге должна существовать в одном экземпляре — в грамматике.**
Сегодня она существует в трёх:

1. в грамматике — метки `Position` у каждого токена;
2. в рендере `Convert.hs` — `wylieFromGlyphs` заново выводит роли из букв по
   шести таблицам, снятым с эталона (`regularStacks`, `caretLetters`,
   `prefixRoots`, `suffixLetters`, `suff2Before`, `ambiguousRoot`);
3. в комментариях и документах — которые это положение дел описывают как
   нормальное.

Три экземпляра не могут не разъезжаться: грамматика разбирает `གརླ` как
префикс+корень+подписную, а рендер — как «корень + корень с подписной», и
печатает `garla`. Обе записи разбираются обратно верно, но об истине договориться
нельзя, пока их две.

Вложенная структура убирает второй разбор **по построению**: у рендера нет
букв, из которых можно вывести роль, — есть только стек с уже назначенной ролью.

## 2. Контракт (правила, которые обязательны для всего дальнейшего кода)

**П1. Роли — только в грамматике.**
Рендер не решает, что такое префикс, корень или суффикс. Если для печати нужен
факт о роли — он приходит из структуры.

**П2. Рендер не додумывает.**
Всё, что нужно для печати, лежит в структуре; рендер только раскладывает её по
алфавиту. Признак нарушения: в рендере появляется таблица букв, вызов парсера
или `case` по набору букв.

**П3. Структура не хранит текста.**
Токен хранит свой срез (это инвариант покрытия входа), но рендер срез не использует:
печать идёт из канонического значения токена и его слота. Срез нужен только
диагностике (цитата) и проверкам покрытия. Слог не хранит ни `raw`, ни копию
потока токенов.

**П4. Нотация — не роль.**
«Как записать стек, чтобы он разобрался обратно» — свойство записи, а не
слога. Оно живёт в Wylie-модуле и опирается на **книжные** правила сочетаний
(4.8–4.10), а не на таблицы эталонного алгоритма. Проверяется round-trip'ом
через наш собственный токенайзер и грамматику.

**П5. Паритет — сверка выхода с корпусами, а не с алгоритмом.**
Оракул — пары «вход → выход» из тестов эталонов (`test/vectors/*.tsv`,
в первую очередь `ewts_js_parity.tsv`). Что у эталона внутри — не наша забота
и не источник кода. Если наш выход расходится с корпусом — это решение,
которое записывается в журнал (§11), а не повод тащить чужую эвристику.

**П6. Ролей нет нигде, кроме слога.**
Нотация (`Join`) говорит, **как знак примкнут к соседнему**, и молчит о том,
**чем является** каждый знак. Роль, слот и границы стеков появляются в
`Syllable` один раз (§4.1). Признак нарушения: поле роли в `notate`/`Join`;
разбор вызывается из рендера; две функции в разных слоях решают, где префикс.

**Признак нарушения контракта** (проверять на ревью): в рендере появилась
таблица букв; рендер использует `tokenRaw`; рендер что-то парсит; две функции в
разных модулях решают, где префикс; роль появилась в нотации.

## 4. Целевые типы

```haskell
-- | Слог = последовательность стеков, написанных слева направо.
data Syllable = Syllable
    { sylStacks :: Seq Stack        -- Seq: число стеков задаёт язык, не контейнер
    , sylSpan   :: Span
    , sylDiags  :: Diagnostics
    }

-- | Стек = одна вертикальная единица письма. Поля фиксированы языком.
data Stack = Stack
    { stRole     :: Role
    , stSuperfix :: Maybe Token     -- надписная буква (полная), максимум одна
    , stRoot     :: Maybe Token     -- корневая буква (может быть подписным токеном)
    , stSubfixes :: Subfixes        -- 0..3 подписные, без дырки
    , stVowel    :: Maybe VowelSlot -- знак гласной или неявная a
    , stCaret    :: Maybe Token     -- ༹, отдельным полем: печатается по-своему
    , stFinals   :: Finals          -- 8 слотов цепочки, каждый не больше раза
    }

-- | Гласная слота. `VowelWritten` — все написанные знаки слота (долгая `I`/`U`/`-I`
--   пишется двумя токенами, форсированный `bru+e` даёт два знака); `VowelImplicit` —
--   неявная `a` (в Wylie пишется буквой, в глифах её нет); `Nothing` в поле —
--   гласной нет вовсе (префикс, суффикс, корень со свёрнутой кареткой f/v).
data VowelSlot = VowelWritten Token [Token] | VowelImplicit

-- | Подписные: закрытый тип, состояния «нет первой, есть вторая» нет.
--   Книга знает не больше двух; третья приходит из санскритской транслитерации
--   (གྨྲྸ) и из форсированных склеек Wylie (`g+m+r+a`). Правило
--   «`l` не бывает второй» живёт в грамматике (`Parser.fitsBelow`), в тип не
--   дублируется.
data Subfixes
    = NoSubfix
    | OneSubfix Token
    | TwoSubfix Token Token
    | ThreeSubfix Token Token Token

-- | Роль стека в слоге. Нужна ровно для двух решений: неявная a и разделитель.
data Role = RolePrefix | RoleRoot | RoleSuffix | RolePostfix
```

`Finals` — отдельный тип, конструктор закрыт: восемь слотов цепочки
(`Token.finalSlot` = 1..8), добавление только через `snoc`, который отказывает,
если слот занят или пройден. Восемь полей `Maybe` дали бы то же, но шумнее.

**Инварианты.**

1. Стеки идут в порядке письма слева направо; знаки внутри стека — в
   каноническом порядке (надписная, корень, подписные, каретка, гласная, финалы),
   а не в порядке, в котором их выдал разбор.
2. Стеков с корнем может быть несколько, и тип это не запрещает. После закрытия
   дыры A их быть не должно: сегодня единственный случай — `མངའ` (два `Root`), и
   он как раз лечится. Пример книги `ཀབ` — не второй корень, а корень+суффикс
   (проверено разбором).
3. Стек без корня — законный случай: слог, открытый гласной, записанной буквой
   (`i` из Wylie). Unicode-рендер пишет перед ним `ཨ` (`ཨི`), Wylie-рендер
   пишет букву как есть (`i`).
4. У стека один слот гласной (но знаков в нём может быть два: долгая пишется
   парой, `bru+e` даёт две), не более одной каретки, не более трёх подписных
   (форма `Subfixes`), не более одного финала на слот (`Finals`).
5. Гласная: `VowelWritten` — знаки из источника, `VowelImplicit` — неявная `a`,
   `Nothing` — гласной нет вовсе (префикс, суффикс, корень со свёрнутой кареткой
   `f`/`v`). Какую из трёх поставить, решает грамматика; рендер `a` не изобретает:
   Wylie печатает `VowelImplicit` как `a`, Unicode не печатает ничего.
6. Каждый токен, которому назначен слот, входит в стек ровно один раз. Съеденные
   знаки, разделители и границы в стеки не входят: первые живут в находках,
   вторые выражены границами стеков, третьи — отдельным элементом (Q4).
7. `Span` покрывает прогон без границы; сам слог границей не владеет (Q4).

`Position` как отдельный тип исчезает на шаге «грамматика»: роль задаётся полем
стека, а слот внутри стека — самим полем.

### 4.1. Слои: знаки → слог; где ветвится письмо

Добавлено 21.10.2026. Раздел отвечает на вопрос, возникший при работе над шагом
2: грамматика ветвится по `Spelling`, потому что различие писем живёт не там,
где ему место. Здесь зафиксировано, где именно, и как это называется.

**Схема (21.10.2026).**

```
вход:   текст → токенайзер → знаки → грамматика → слог
выход:  юникод: текст ← рендер ← слог
        вайли:  текст ← рендер ← notate ← слог
```

Грамматика одна на оба письма. Письмо ветвится ровно в двух местах: **в чтении**
(два токенайзера) и **в печати** (рендер юникода против `notate` + рендер вайли).
Между ними — общий домен `Syllable`; структуры, размеченной письмом, нет.

**Почему входных структур нет.** Решение 21.10.2026; отменяет `UnicodeSyllable` и
`WylieSyllable` на входе. Критерий: тип оправдан, только если делает
недопустимое состояние непредставимым. `Syllable`/`Stack` — оправдан: «токен без
роли», «две гласные в стеке», «финал вне слота» в нём невозможны. Входные
структуры — нет: это тот же поток знаков, порезанный иначе; грамматике они
ничего не запрещают, а названный этап требует кода, который ничего не решает.
Различие письмён и без них выражено **в знаке**: подписанность — `TcSubConsonant`
против полной буквы (`isSubjoinCandidate`), неявная `a` — буква `a` в вайли
(`isImplicitAWylie`), разделители — `CSDot`/`CSPlus`. Поэтому `Spelling` не
возвращается: грамматика спрашивает не «какое письмо», а «может ли этот знак
занять слот».

**Что осталось от идеи: нотация на выходе.** В вайли знака «подписанная» нет,
поэтому границу записи выбирает не рендер, а `notate :: Syllable
-> Seq (Join, Token)`, где `Join` — как знак примкнут к предыдущему (`JSolid`,
`JPlus`, `JDot`). Рендер вайли становится раскладкой; юникодному спуску места нет
— порядок полей слога и есть порядок глифов. Таблица сочетаний (4.8–4.10) живёт в
`Convert.Wylie.Tables`.

**Как это выглядит сегодня** (21.10.2026: что уже есть и где протекает):

| слой | сегодня | протечка |
|---|---|---|
| знаки | `Convert.Token` | — |
| чтение | `tokenizeUnicode` / `tokenizeWylie` | — |
| разбор | `pSentence :: Spelling -> Parser [SpellItem]` | `Spelling` в констрейнтах: 01, 08, 09, 10 ветвятся по письму |
| структура | `Seq (Maybe Position, Token)` | стек, роль и слот не тип; разделители — токены без метки; `Eaten` — позиция |
| печать юникода | `renderSyllable` (`Convert.hs`) | читает `tokenRaw`, решает подписанность (`runReachesVowel`), дописывает `ཨ` |
| печать вайли | `renderSyllableWylie`, `wylieFromGlyphs` | второй парсер ролей: шесть таблиц эталона |
| нотация | нет | `+`/`.` — обычные токены: смысл есть, слота нет |

**Словарь (обязателен в коде и документах).**

| термин | что это | в коде |
|---|---|---|
| **знак** | один размеченный срез текста после токенайзера: срез, канонический класс, источник, спан | `Token` |
| **поток знаков** | плоский список знаков, без структуры слога | `[Token]`, `Seq Token` |
| **слог** | домен: стеки с ролями и слотами | `Syllable`, `Stack` |
| **разбор** | переход «поток знаков → слог»; это и есть грамматика | `Convert.Grammar.*` |
| **нотация** | как записать стек, чтобы он разобрался обратно; свойство записи, а не слога | `Join`, `notate` |
| **спуск** | переход «слог → запись»: только вайли (`notate`), у юникода тождествен | `Convert.Wylie.Tables` |

Слова «wire», «DTO», «транспортная структура», «структура записи» не
используются: первые три пришли из другой задачи (сериализация), а «запись» в
этом документе уже занята манерой письма («слитная запись», «Wylie-запись»).
Термины «промежуточная структура», «вертикальная единица» и «кластер» из работы
уходят вместе с решением 21.10.2026: они называли этап, которого нет.

**Отменено 21.10.2026: гарантия письма как тип.** Здесь стояла таблица «что несёт
промежуточная структура» и довод «две структуры, а не одна с ярлыком»: у юникода
группировка знаков — факт, у вайли — предложение. Довод верен как описание
письма, но типом он не становится: гарантия уже выражена классом знака
(`TcSubConsonant` против полной буквы), а второй экземпляр того же факта — ещё
одно место, которое может разъехаться. Опыты E1/E2 (§4.1, «Следствия») проверяют,
что гарантии знака достаточно; «нет» в E1 возвращает входную структуру для
юникода.

**Чего разбор не отменяет.** Таблицы 4.8/4.10 (какая буква надписная, какая
корень) и группы 4.11–4.16 (роли стеков) остаются в грамматике: письмо их не
выражает. Примеры: `སྒྲྭ` — одна вертикаль `ས ྒ ྲ ྭ`, но кто в ней надписная,
решает 4.8 (дыра A3); `grla` — одна слитная запись, которую грамматика делит на
`ག` + `རླ`; `gyi` и `g.yi` различаются в юникоде знаком, а в вайли точкой, и оба
различия — нотация, не роль.

**Что это убирает.** Параметр `Spelling` из констрейнтов (шаг 4): констрейнт
спрашивает не «какое письмо», а «может ли этот знак заполнить слот» — предикат
по знаку. Половина этого уже есть в `Parser` (`isSubjoinCandidate`,
`isEatableVowel`), но рядом живёт второй механизм — параметр `Spelling`, и они
расходятся. Остаётся один механизм — предикат по знаку.

**Следствия для шагов.**

- шаг 2 не меняется: A и A2 решаются в грамматике;
- шаг 3: появляется `notate :: Syllable -> Seq (Join, Token)` — только для
  вайли; юникодный рендер печатает поля слога по порядку, спуск ему не нужен.
  Нотация — это данные (`JSolid`, `JPlus`, `JDot`, неявная `a`), а не набор
  функций;
- шаг 4: вход разбора остаётся `Seq Token`; `Spelling` удаляется, его место
  занимает предикат по знаку; `Position` и `stacksOf` умирают;
- проверка схемы — опыты, а не прототип: **E1** на юникодных корпусах — каждая
  вертикаль (основа, подписные, гласная, финалы по классу знака) содержит ровно
  один стек снимка шага 1; **E2** на вайли — ни один стек не пересекает
  написанную гласную. Оба «да» подтверждают схему; «нет» в E1 — единственный
  повод вернуть входную структуру для юникода.

| `བཀྲ` | `[Prefix b]`, `[Root k, Subfix r]` | `bkra` | བཀྲ |
| `གཡུལ` | `[Prefix g]`, `[Root y, Vowel u]`, `[Suffix l]` | `g.yul` | གཡུལ |
| `མངའ` | `[Prefix m]`, `[Root ng]`, `[Suffix ']` | `mnga'` | མངའ |
| `བཾྲ` | `[Root b, Subfix r, Finals M]` | `braM` | `བྲཾ` (канон) |
| `རྐ` | `[Superfix r, Root k]` | `rka` | རྐ |
| `ཨུ` | `[Root a, Vowel u]` | `u` | ཨུ |
| `གྲླ` | `[Root g, Subfix r, Subfix l]` | `g+r+la` | གྲླ |
| `གྨྲྸ` | `[Root g, Subfix m, Subfix r, Subfix a]` | `g+m+r+a` | གྨྲྸ |
| `དྷ` | `[Root d, Subfix h]` | `d+ha` | དྷ |
| `ཕ༹` | `[Root ph, Caret]` | `f` | ཕ༹ |

Unicode-колонка — **канонический** вывод (порядок полей), а не исходное
написание: `བཾྲ` на входе даёт `བྲཾ` на выходе. Это то же самое, что
`U→W→U`, просто без шага в вайли.

`མངའ` — единственная строка, где сегодняшние метки **глифового разбора** не
годятся: грамматика ставит `འ` в `Root` (см. §8 A). **Решение 21.10.2026:** голая
`འ` в хвосте слова — `Suffix`. Та же строка в Wylie (`mnga'`) читается книжной
структурой 9 и уже даёт `Suffix`; после A2 одно слово даёт **один** AST в обоих
письмах.

## 6. Алгоритмы рендера (после рефакторинга)

**Wylie** — по стекам слева направо:

1. буквы стека: надписная, корень, подписные → мнемоника через `wylieOf`;
2. склейка букв внутри стека: слитно, если сочетание книжное (4.8–4.10), иначе
   через `+` (`g+r+la`, `d+ha`); данные — `Convert.Wylie.Tables`;
3. каретка: свёртка `ph+каретка → f`, `b+каретка → v` (данные — из
   `wylieExpansions` токенайзера), иначе `^`. У такого корня неявной `a` нет —
   это решила грамматика, положив `Nothing` в `stVowel`;
4. гласная: `VowelWritten` — мнемоника (`ཱ` + краткая = одна долгая `I`, `U`,
   `-I`); `VowelImplicit` — буква `a`. Рендер ничего не дописывает;
5. финалы: мнемоники в порядке цепочки;
6. между стеками: `.` только если слитная запись разобралась бы как один стек
   (иначе `g` + `y` дало бы `gy` вместо префикса с корнем).

**Unicode** — по стекам слева направо, в порядке полей:

1. надписная → полный глиф;
2. корень: если токен **уже подписной** (`TcSubConsonant`, пришёл из Unicode) —
   печатать подписным глифом всегда (иначе `རྐ` перестанет быть собой); если
   токен полная буква (пришёл из Wylie) — подписным, только когда стек доходит до
   гласной (`rka` → རྐ, но `rk` → ར + ཀ);
3. подписные → подписные глифы;
4. стек без корня, открытый гласной → `ཨ` перед знаками;
5. корень `a` с гласной → `ཨ` перед знаком гласной;
6. каретка → `༹`;
7. гласная → её глиф; `VowelImplicit` не печатает ничего (это и есть неявная `a`);
8. финалы → их глифы;
9. между стеками ничего не печатается.

Порядок **канонический**, по полям: исходный порядок знаков не сохраняется
(`བཾྲ` → `བྲཾ`). Это же правило делает `U→U` идемпотентным.

Обе схемы — обход структуры. Ни одна не смотрит на `tokenRaw`, ни одна не
вызывает парсер, ни одна не содержит таблиц букв.

### 6.1. Зачем нужна нотация (и почему это не костыль)

В Unicode у подписанной буквы свой кодпоинт: `གྲླ` = `ག` + `ྲ` + `ླ`,
двусмысленности нет — рендер просто выкладывает то, что лежит в стеке.

В Wylie знака «подписанная» **нет**: подписанность выражается только соседством
букв, и одну и ту же последовательность конвертер W→U разбирает по грамматике.
Проверено на нашем же разборе W→U:

> **«Разбирается так же» означает:** если подать эту запись на вход конвертера
> W→U (`tokenizeWylie` + грамматика, те же модули, что работают при обычной
> конвертации), получится та же структура слога. Рендер — обратное направление,
> к этому определению отношения не имеет.

| запись | разбирается как | почему |
|---|---|---|
| `grla` | གརླ | разбор W→U предпочёл префикс `g` + корень `r` + подписную `l` |
| `g+r+la` | གྲླ | явная склейка: один стек `g`+`r`+`l` |
| `gyul` | གྱུལ | надписная `g` над корнем `y` |
| `g.yul` | གཡུལ | точка разрывает стек: префикс `g`, затем стек `y`+гласная |

Значит роли в структуре **недостаточно**: она говорит, что должно получиться, но
не говорит, разберёт ли конвертер W→U слитную запись в ту же структуру. Отсюда
обязательный шаг «слитная запись разбирается иначе?» — это и есть нотация. Роли
в нём участвуют (из них видно, где граница стеков), но не пересчитываются: они
приходят из структуры.

Это не костыль, а свойство формата вывода — как кавычки или escape в любой
сериализации. Костылём оно становится, только если ответ на «разбирается ли
иначе» берётся из чужого алгоритма вместо нашего разбора W→U или книги.

Три способа получить это знание:

1. **Считать на лету** round-trip'ом через наш токенайзер и грамматику — точно и
   без таблиц, но дорого: 37 структур пробуются на каждый слог.
2. **Таблица книжных сочетаний** 4.8–4.10 — быстро и консервативно; одна
   таблица, данные из книги, а не из эталонного алгоритма.
3. **Всегда явно** (`r+g+ya`) — знание не нужно вовсе, но запись нечитаема и
   паритет рушится.

Принято: вариант 2, таблица живёт в отдельном модуле `Convert.Wylie.Tables`
(там же функции записи, чтобы не плодить второй модуль).

**Экзотика лечится умолчанием, а не новой таблицей.** Книжная таблица только
*разрешает короткую запись*; всё, чего в ней нет, пишется явно:

- внутри стека: сочетание не книжное → `+` между буквами (многословно, но
  однозначно);
- между стеками: пара букв на границе не книжная → точка не нужна, потому что
  разбор W→U и так разорвёт стек в этом месте.

Поэтому незнакомая комбинация не требует ни новой записи в таблице, ни новой
ветки в рендере: она получает явную запись по умолчанию. Если явная запись не
разбирается обратно — это дефект `+`/`.`, а не повод расширять таблицу.
Расширять её можно только книжными данными.

## 8. Дыры, которые надо закрыть до/во время рефакторинга

**A. Роль за пределами книги (а-чунг).**
`མངའ` разбирается структурой 35 (4.14 + 4.20) как `Prefix m + Root ng + Root '`
(замер 21.10.2026; раньше здесь было записано «структурой 38» — неточно: при
равной длине 35 стоит в списке раньше). Книга такого слова не описывает (а-чунг
не суффикс 4.3 и не постфикс 4.4), эталон принимает, рендер лечит таблицей
`suffixLetters`.
**В ROADMAP как дефект не записано** — записано как достижение шага 5.7
(`མངའ → "mnga'"`, ROADMAP ~869).
**Решение (принято 21.10.2026):** грамматика обязана назвать роль последнего
стека (`Suffix`), а не оставлять `Root`. Это наше решение там, где книга молчит,
и оно должно быть названо нашим (hewts.md §2), а не таблицей в рендере. Где
именно: `འ` — корень только когда при нём есть своя гласная или второй корень
(`ཧིའེ`, `འང`); голая `འ` в хвосте слова — суффикс. Названо в хвосте слова
(структуры 28–37), правило 4.20 не меняется — см. §11. **Сделано 21.10.2026:**
`Constraint20.pConstraint20` (§9, шаг 2).

**A2. Роли в Wylie-ветке.** `g.yul` разбирается как `Root g` + `Root y` +
`Root l` (проверено), хотя по смыслу это префикс + корень + суффикс. Причина —
разрешающая структура 38: книжные цепочки точку не принимают. Решение — Q9: чиним
книжные цепочки, одно слово даёт один AST.
**Принято 21.10.2026:** точка принимается **на границе префикс→корень** внутри
4.14; после точки действует полная книжная группа корней (`g.yi` = གཡི, а не
`gyi` = གྱི). Прочие границы стека (после корня, перед суффиксом) остаются за
структурой 38 до шага 3/4 — это `shortcut`, а не решение. `pRoots1Wylie` при
этом умирает: урезанная группа была свойством записи, а не грамматики (§4.1).
**Сделано 21.10.2026:** `Constraint14.parseConstraintWylie14` берёт точку и
проверяет подписной знак предикатом; `pRoots1Wylie` удалён.

**A3. Надписная при трёх подписных знаках (Unicode).**
`སྒྲྭ` — это `ས` надписная + `ྒ` корень + `ྲ`/`ྭ` подписные, но книжные
структуры принимают не больше двух подписных знаков, поэтому побеждает
обобщённая структура 38 и ставит `ས` в `Root`. Шаг 1 воспроизводит это как
`Root ས` + `ThreeSubfix ྒ ྲ ྭ`; это не пример третьей подписной, а потерянная
надписная. Чинится в грамматике (шаг 3/4; в приёмку шага 2 не входит): подписной
корень под надписной надо распознать по таблице 4.8 и провести как `Root`, а не
как `Subfix`. В мосте это было бы вторым парсером, поэтому мост не чинится.

**B. Разделители не имеют слота.**

Простыми словами: `.` и `+` — это не буквы, а **разметка для обратного
разбора**: «здесь
разрыв стека» и «здесь принудительная склейка». В Unicode таких команд не нужно
(там всё выражено кодпоинтами), в Wylie они единственный способ выразить
границу. Сегодня токенайзер делает из них токены, грамматика их съедает, а в
плоской структуре им нет места — они лежат там как «токены без метки», и рендер
их молча выбрасывает.

Чем это плохо:

1. `W→W` теряет точку и меняет слово: `g.yul` (གཡུལ) → `gyul` (གྱུལ).
2. `U→W` не может их переиздать — ему приходится заново выводить границы
   стеков из букв, а это и есть второй парсер.
3. Диагностика их видит, печать — нет: одна и та же структура значит для двух
   потребителей разное.

Опции:

| вариант | что делаем | плюсы | минусы |
|---|---|---|---|
| **B1. Хранить** | кладём разделители в структуру (поле стека или слога) | `W→W` побайтово точен, ничего не теряется | две правды о границе (токен и граница стека); пользовательская точка может противоречить нашей; структура перестаёт быть канонической |
| **B2. Выбросить** — **принято 20.10.2026** | разделитель — синтаксис входа; его смысл уже выражен границей стека | одна правда; второй парсер не нужен; оба бага исчезают | `W→W` может расставить разделители иначе (текст другой, глифы те же) |
| **B3. Хранить только «принудительные»** | держим `+`, который структура объяснить не может | ловит экзотику (`rdo+e`) | если структура всё объясняет — хранить нечего |

**Что именно несёт структура вместо разделителя:** факт, а не разметку. Для
`.` факт — «здесь граница стека» (границы стеков в структуре есть). Для `+`
факт — «эти буквы принадлежат одному стеку» (состав стека в структуре есть).
Сама запись (точка или выписанная `a`, `+` или слитно) — решение нотации и
храниться не должна.

**Почему B2.** Разделитель не несёт того, чего нет в структуре: он говорит
ровно «здесь граница стека» или «склей эти буквы». И то и другое структура
знает. Хранить его отдельно — значит разрешить двум источникам противоречить
друг другу (пользователь написал `.` там, где структура видит один стек), и
ровно на этом противоречии живёт сегодняшний баг `g.yul → gyul`. B1 переносит
это противоречие в структуру и делает её неканонической; B3 сводится к B2,
потому что «принудительная склейка» — это и есть обычный стек, только полученный
из `+`; после разбора он ничем не отличается от книжного.

Диагностика при этом ничего не теряет: находки о лишней/незабранной точке
записываются в момент разбора, а цитата вычисляется по спану в исходном тексте,
а не берётся из структуры (П3).

Проверка: не «`W→W` совпадает посимвольно», а «`W→U→W→U` даёт те же глифы» на
всех корпусах, плюс `U→W→U`. Посимвольное совпадение `W→W` продуктовым
требованием не является.

**C. `Constraint21` и `Constraint22` — не книжные правила.**

Оба модуля появились по ходу работы над Wylie поверх плоского AST, а не из книги:

- `Constraint21` — разрешающий «хвост слова» (он же структура 38): принимает то,
  чего книжные структуры не принимают (точки, лишние буквы), и на таких формах
  выигрывает у книги, назначая всем подряд роль `Root`;
- `Constraint22` — окно с семью выписанными формами и рекомендацией написания.

Поэтому это не «раздутые полезные модули», а компенсация отсутствия стека и ролей.
После Q9 и шага 4 их работу должны делать книжные структуры; что осталось — Q3.

Это же объясняет, откуда взялись таблицы в рендере: разрешающая структура оставляла
роли корявыми, и рендер вынужден был их угадывать. Лечим причину, а не следствие.

### 9.1. Проверки (корпус — генератор)

1. **Покрытие.** Каждый токен прогона входит ровно один раз: либо в стек, либо в
   `[Token]` невалидного прогона. Разделители и съеденные знаки отсутствуют
   ожидаемо.
2. **Канонический порядок.** В каждом стеке знаки лежат в порядке полей
   (надписная, корень, подписные, каретка, гласная, финалы), финалы — в порядке
   слотов. Проверяется прямо на AST.
3. **Один слог — один AST.** `གཡུལ` и `g.yul`, `མངའ` и `mnga'` дают одинаковую
   форму: роли, согласные, написанные гласные, финалы. Сравнение по проекции
   формы, без `tokenRaw` и `Span`. Неявная `a` в сравнение не входит: она —
   синтаксис входа (в Wylie написана буквой, в глифах её нет), и знака, которым
   её можно пометить в юникоде, на плоском типе не существует.
4. **Round-trip.** `U→W→U` на корпусах даёт те же глифы; `W→U→W→U` стабильно.
5. **Нотация.** Каждая запись книжной таблицы, написанная слитно, разбирается
   обратно в тот же стек; сочетание вне таблицы получает `+` и тоже читается
   обратно.
6. **Канон.** `renderItems OutUnicode` идемпотентен; `syllables` идемпотентна на
   своём выводе.

## 10. Вопросы

### 10.1. Решённые

**Q1. Как рендер решает, где ставить разделитель? — решено 20.10.2026: вариант 2.**
Простым языком: Wylie не умеет сказать «эта буква подписанная» — только
соседством. Поэтому одна и та же запись разбирается по-разному (`grla` = གརླ,
`g+r+la` = གྲླ; `gyul` = གྱུལ, `g.yul` = གཡུལ`). Нужен ровно один ответ на
вопрос «слитная запись разберётся иначе?».

Варианты:

1. **Считать на лету** прогоном через наш конвертер W→U (токенайзер + грамматика). Точно по
   определению, таблиц нет, но каждое решение — это повторный разбор, а разбор
   у нас пробует 37 структур.
2. **Таблица книжных сочетаний 4.8–4.10** (какие стеки законны). Быстро,
   консервативно, и совпадает с эталоном, потому что эталон следует той же
   книге. Одна таблица, данные — книжные, не из алгоритма эталона.
3. **Всегда явно** (`r+g+ya`, `g.yul` везде). Знания не нужно, но запись
   нечитаема и паритет рушится.

**Принято 20.10.2026: вариант 2.** Причина не в скорости, а в том, что наш выход
будут разбирать и чужие EWTS-конвертеры: `dh` — наша поблажка-алиас, в вывод её
тащить нельзя, а `d+ha` — стандартная запись. Плюс проверка round-trip'ом на
корпусах всё равно остаётся: таблица обязана совпадать с «разбирается в ту же
структуру».

**Q2. Что делать, если наш выход расходится с ожиданием корпуса? — решено: грамматика побеждает.**

Простым языком. Паритет устроен так: в файлах эталонов лежат пары «вход →
ожидаемый выход». Мы прогоняем свой конвертер и сравниваем текст. Обычно
совпадает. Проблема возникает на слогах, где **эталон при печати угадывает роль
буквы по своей таблице, а не по грамматике**. Примеры уже известны:

- `དགས`: мы печатаем `dags` (по нашим ролям: корень + суффикс + постфикс),
  эталон ждёт `dgas` (его эвристика ставит `d` префиксом). Записано в
  ROADMAP 3.4.11.
- `གརླ`: мы будем печатать `g.rla`/`grla` (префикс + стек), эталон печатает
  `garla` (он не считает `g` префиксом перед `r+l`).

Всё это разбирается обратно в те же глифы, но текст другой. Когда вылезет: на
шаге 3, сразу после удаления таблиц ролей, — упадёт `u2w` в отчёте паритета.

Рассмотренные варианты: (1) считать своим дефектом и подгонять под эталон — это
возвращает таблицы ролей с чёрного хода; (2) принять расхождение и записать
каждый случай; (3) останавливаться и спрашивать на каждом.

**Принято 20.10.2026: вариант 2.** Грамматика — источник истины; эталонная
эвристика ролей не воспроизводится. Число в храповике `u2w` опускается, запись —
§11.1.

**Q4. Границы (цек/пробел) — внутри слога или отдельный элемент? — решено: отдельный.**
Токены для цек/пробела уже есть (`TcPunctuation`, `TcSpace`), токенизация их не
теряет. Вопрос только в том, где они лежат: сейчас — хвостом внутри элемента
слога, после — самостоятельным элементом (`Punct`). Новый конструктор не нужен:
`Punct` уже есть, а отличать границу от прочей пунктуации незачем — она и так
исключена из всех проверок.

**Q6. Съеденные знаки (вторая каретка, точка без стека) — решено: в структуру не попадают.**
В чём была проблема: сегодня такой знак лежит в плоском списке с меткой `Eaten` —
грамматика его «забрала и назвала», печатать его нельзя, но он остаётся в потоке,
чтобы предупреждение могло его процитировать. В новой структуре для него нет
места: он не буква, не гласная и не финал. Решение: не хранить.

Почему диагностика от этого не страдает:

- находка создаётся **в момент разбора**, когда знак ещё в руках у грамматики, и
  несёт в себе всё нужное: например `SecondCaret` для второй каретки;
- цитата в предупреждении — это не текст из структуры, а **позиция в исходном
  тексте**: `Diagnostic` хранит `diagSpan` и `diagWord :: Maybe Span`, а строка и
  цитата вычисляются один раз на границе из входного `Text`;
- значит структуре нечего хранить для диагностики: ни `Eaten`, ни «мусорного»
  поля ей не нужно.

Проверка — на шаге «переключение» (типы) и на шаге «грамматика»: ни одна находка не
должна перестать срабатывать.

**Q5. `+` и `.` во входе — синтаксис или факт? — решено в §8B (B2): синтаксис.**
Разделитель — разметка для обратного разбора; сам факт («здесь граница стека»,
«эти буквы — один стек») уже выражен структурой.

**Q8. `syllables :: Text -> Either Text [Text]` — решено: возвращает канонический вид.**
Функция извлекает слоги, но печатает их тем же каноническим рендером, что и
`renderItems OutUnicode`: `syllables "བཾྲ"` = `["བྲཾ"]`. Это не «написание как в
тексте» — определение функции меняется и должно быть переписано.
Причины: внешних вызовов у функции нет (в `hibet/hibet` свой разбор), в
каноническом виде один путь печати вместо двух, и `syllables` идемпотентна на
своём же выводе. Связь с исходником («найти слог в тексте») при этом теряется, но
смещений функция и так не возвращает.

**Q12. Подписные в стеке: закрытый тип, а не два `Maybe` — решено.**
Два поля `Maybe` разрешают состояние «нет первой, есть вторая», которого язык не
знает: прогон подписных строится по одной букве слева направо
(`Parser.pSubjoinRun`). Поэтому `Subfixes = NoSubfix | OneSubfix Token |
TwoSubfix Token Token | ThreeSubfix Token Token Token`, конструкторы закрыты.
Книга знает не больше двух; третья — санскритская транслитерация (`གྨྲྸ`)
или форсированная склейка Wylie (`g+m+r+a`). Правило «`l` не бывает
второй» остаётся в грамматике (`fitsBelow`), в тип не дублируется.

**Q9. Роли в Wylie-ветке (`g.yul` = три `Root`) — решено 20.10.2026: чинить грамматику.**

**Что происходит.** Одно и то же слово, записанное двумя письмами, даёт два разных
AST (проверено разбором):

| вход | разбор |
|---|---|
| གཡུལ | `[Prefix g]`, `[Root y + u]`, `[Suffix l]` |
| `g.yul` | `[Root g]`, `[Root y + u]`, `[Root l]` |

**Почему так вышло.** Книжные структуры 1–37 точку между префиксом и корнем не
принимают. Поэтому на `g.yul` выигрывает самая длинная — разрешающая структура 38
(`pConstraint21First` + хвост `pConstraint21Rest`), а её хвост съедает точку
(`pDotBreak`) и помечает каждый следующий стек как `Root`. Ни структура 38, ни
`Constraint22` не книжные: они появились по ходу работы над Wylie поверх плоского
AST.

**Решение.** Одно слово — один AST. Точка как разделитель стеков принимается
**книжными цепочками** там, где кончается один стек и начинается следующий; после
этого разрешающая структура 38 перестаёт выигрывать на `g.yul`, и роли приходят из
книжного разбора. Роль надстроек 21/22 переходит к книжным структурам (Q3).

**Цена.** Могут сдвинуться находки диагностики: окна префиксов начнут срабатывать
там, где раньше молчала структура 38. Паритет по тексту меняться не должен —
проверяется тестом.

### 10.2. Открытые

**Q3. Что делать с `Constraint21` и `Constraint22` после шага 4.**

Оба — не книжные правила, а наши надстройки, появившиеся под плоский AST:
`Constraint21` — разрешающий «хвост слова» (структура 38), `Constraint22` — окно с
семью выписанными формами и рекомендацией написания.

После Q9 и шага 4 их работу должны делать книжные структуры. Что осталось — решаем
после шага 4: удалить целиком, оставить только честный fallback для нечитаемого
входа (и тогда он не назначает роли), или сохранить `22` как нашу диагностику.
До шага 4 не трогаем, кроме минимума, нужного для Q9.

**Q10. Порядок структур при равной длине (tie-break).**

Простыми словами: длину совпадения грамматика считает сама — пробует все 38
структур и берёт самую длинную. Поэтому список `candidates` решает только ничьи:
когда две структуры покрыли одинаковое число знаков, а роли расставили разные.
Сейчас этот список сколочен по волнам работы и книжным порядком **не является**,
хотя комментарий в `Convert/Sentence.hs` (~413-416) обещает обратное.

Замер 21.10.2026 (все 38 структур на первом слоге каждой строки всех корпусов;
ничья — две структуры с одинаковой максимальной длиной и разными метками):

- вайли: 63 строки с ничьей, и во всех соперник — структура 38. Она всегда
  последняя, поэтому книга выигрывает, а порядок книжных структур в вайли не
  решает ничего;
- юникод: ничьи «книга против книги» — три семьи: `08`/`17` (18 строк),
  `09`/`21` (40), `09`/`35` (5). Остальные ничьи — против 38.

| семья | пример | чтения | кто выигрывает сейчас |
|---|---|---|---|
| `08`/`17` | `བཀ` | префикс+корень / корень+суффикс | 08 (префикс) |
| `09`/`21` | `དགས` | префикс+корень+суффикс (`dgas`) / корень+суффикс+постфикс (`dags`) | 21 (`dags`) |
| `09`/`35` | `མངའ` | суффикс / корень (а-чунг) | 35 (корень) |

Варианты: (1) оставить как есть и переписать комментарий честно; (2) книжный
порядок 1…37, 38 последней; (3) придумать метрику специфичности.

**Предложение:** (2). Оно делает комментарий правдой и меняет ровно одну семью —
`09` побеждает `21`, то есть `དགས` читается как `dgas`: так его рекомендуют и
корпус, и наша же диагностика (`Constraint22`). Семья `09`/`35` исчезает после
решения A, `08`/`17` не меняется. Текст вывода от ролей сегодня не зависит,
поэтому паритет не должен поехать, но проверяется замером. (3) — новая правда
вместо книжной, не рекомендуется.

**Не решено.** Решение принимается до шага 2 или переносится на шаг 3; до него
комментарий в `Convert/Sentence.hs` не трогаем.

**Q11. Может ли вертикальная единица юникода требовать разбиения на два стека?**

Гипотеза: нет. Письмо пишет вертикаль, поэтому единица и есть стек; грамматика
решает только, какая буква единицы надписная и какую роль играет стек. Проверка —
опыт **E1** (§4.1): на всех юникодных корпусах каждая вертикаль (основа,
подписные, гласная, финалы по классу знака) даёт ровно один стек снимка шага 1.
«Нет» в E1 — единственный повод ввести входную структуру для юникода; тогда же
она получает право дробить вертикаль.

**Q13. Нужна ли `WylieSyllable` на входе? — решено 21.10.2026: нет.**

Кластер вайли не содержит ничего, кроме знаков между написанными гласными и
разделителями: ни вертикали, ни ролей письмо не выражает, а стек всё равно
кончается на гласной и на границе, которую называет книга. Входной вайли-структуры
не вводим: разбор читает поток знаков. Опыт **E2** (§4.1) — проверка, что ни один
стек не пересекает написанную гласную. На выходе нотация остаётся, но живёт
функцией `notate`, а не типом слога.

### 11.1. Где живёт запись о расхождении

Три уровня, у каждого своя роль:

| что | где | кто читает |
|---|---|---|
| решение как принцип (дата, формулировка, следствие) | §11 этого файла, таблица | человек, при разборе «почему так» |
| конкретные случаи (вход, наш выход, ожидание эталона, причина) | `hewts/test/parity/known_divergences.tsv` | тест паритета и человек |
| число в храповике | `hewts/test/parity/parity_baseline.tsv` | тест паритета |

Формат `known_divergences.tsv` (создаётся на шаге 3, когда появятся первые
случаи):

```
# корпус <TAB> строка <TAB> вход <TAB> наш выход <TAB> ожидание эталона <TAB> причина
u2w	jsewts	དགས	dags	dgas	роли по грамматике: корень+суффикс+постфикс
```

Правила: причина — обязательна и объясняет, **почему наша запись верна** (а не
«эталон неправ»); тест паритета помечает эти строки как ожидаемые расхождения и
падает, если такая строка начала совпадать (значит, случай закрылся и строку пора
удалить). В шапке `parity_baseline.tsv` и в разделе волны ROADMAP — одна строка
со ссылкой на файл.

## 12. Риски

1. **Объём шага 4.** Трогаются 37 структур и 22 модуля констрейнтов, но
   большинство только собирает метки; разбирают список целиком ровно два места —
   `Constraint22` и `Convert.Sentence.pSyllable.runItems` (склейка размеченных и
   неразмеченных токенов по исходному порядку). Главный риск — не объём, а
   неучтённые `case` по меткам и потеря порядка при склейке.
2. **Роли вне книги.** Если грамматика не назовёт роль, структура этого не
   спрячет: она станет блокирующей. Это плюс для корректности, минус для сроков.
3. **Паритет.** Ожидаемая дельта — `གརླ` (`grla` вместо `garla`). `ཕ༹` после
   шага «переключение» станет `f`, как у эталона, то есть `u2w` на этом слоге
   вырастет. Аспираты (`d+ha`) совпадут, **если** книжная таблица сочетаний
   совпадёт с эталонной — это проверяется на шаге «переключение». Каждая дельта —
   запись в §11.1, не «шум».
4. **Снимки.** Golden-файлы придётся перегенерировать один раз; это должно быть
   отдельным коммитом с объяснением, иначе регресс спрячется в диффе.
5. **Входных структур нет.** Схема держится на том, что вертикаль юникода уже
   размечена классом знака. Если E1 даст «нет» (единица требует двух стеков),
   юникоду понадобится входная структура, и её придётся вводить до шага 4.
